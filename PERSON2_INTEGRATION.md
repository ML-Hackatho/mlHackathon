# Person 2: model experiments and API

Person 2's implementation uses the actual candidate exports generated by Person 1. Both classifiers use the exact 15 ordered columns in `pathsnap_person1.features.FEATURES`, with `is_target=True` as the positive class. Candidate-miss observation groups are excluded from model fitting and retained in evaluation.

## Reproduce the model experiments

From the repository root in PowerShell:

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m pip install -e .
python -m pathsnap_person2.training --candidate-dir .\outputs\shivanand_handoff --out .\outputs\person2 --folds 5 --trials 5
```

The training script runs five-fold GroupKFold by `trip_id` on the 80 training trips, compares initial LightGBM and XGBoost settings, selects the higher mean per-trip observation Macro F1, and tunes that model with Optuna's TPE sampler. The objective is mean per-trip observation-level Macro F1 over the same training folds. The 10 student-test trips are evaluated only after tuning; they are not used for model selection or hyperparameter search. Evaluator data is never read.

Key outputs are in `outputs/person2/`:

- `model_comparison_results.csv` and `grouped_cv_folds.csv` - fold and student-test metrics;
- `optuna_trials.csv`, `optuna_study.db`, and `tuning_summary.json` - trial history, study storage, search space, and best settings;
- `training_summary.json` and `training.log` - counts, feature order, package versions, model settings, and run details;
- `model_comparison.png` - plots made from actual CV and student-test results;
- `models/lightgbm_baseline.json` and `models/xgboost_baseline.json` - baseline configurations;
- `models/final_model.joblib`, `models/final_model.ubj` (XGBoost native copy), and `models/final_model.json` - selected tuned model, parameters, and metadata.

## Retune the HMM for the selected model

The decoder is adapted from Shreya's updated `person3_route_decoding_ui` HMM and receives Person 1 candidate rows. Its emissions are the selected model's `predict_proba(X)[:, 1]` values. Because Shreya's existing decoder settings were tuned for the MLP, generate XGBoost out-of-fold scores and tune the decoder on training trips before using it for the final model:

```powershell
python -m pathsnap_person2.oof --candidate-dir .\outputs\shivanand_handoff --out .\outputs\person2 --folds 5
python -m pathsnap_person2.decoder_tuning --candidate-dir .\outputs\shivanand_handoff --data-root '.\data\Student folder' --out .\outputs\person2 --trials 30
```

The tuning command writes `models/decoder_config.json`, OOF trial records, and training-only comparisons. It then evaluates classifier-only versus HMM/Viterbi on the 10 student-test trips and saves per-trip results, summary metrics, and a comparison plot. Student-test data is not used to tune the decoder.

## Run the API

The API loads the selected classifier once and serves trips from a directory containing one subfolder per trip. Each trip folder must contain `<trip_id>.track`, `<trip_id>.nodes`, and `<trip_id>.arcs`. Prediction never reads `.route`; if a route file exists, the API reads it only after prediction and returns aggregate evaluation values.

For local development with the student-test trips:

```powershell
$env:PATHSNAP_TRIPS_DIR = (Resolve-Path '.\data\Student folder\student_test').Path
$env:PATHSNAP_PARTITION = 'student_test'
$env:PATHSNAP_MODEL_FILE = (Resolve-Path '.\outputs\person2\models\final_model.joblib').Path
$env:PATHSNAP_DECODER_CONFIG = (Resolve-Path '.\outputs\person2\models\decoder_config.json').Path
$env:PATHSNAP_CORS_ORIGINS = 'http://localhost:5500'
python -m pathsnap_person2.api
```

For the evaluator demo, set `PATHSNAP_TRIPS_DIR` to the approved evaluator trip directory and `PATHSNAP_PARTITION` to `evaluator_test`. Keep evaluator trips out of training, model/decoder tuning, and UI code. Start the UI on Laptop 2 at port 5500 and allow inbound port 8000 on Laptop 1's firewall. If the UI uses a different origin, set that exact origin in `PATHSNAP_CORS_ORIGINS`.

Endpoints:

- `GET /health` - selected model and API status;
- `GET /trips` - available trip IDs;
- `POST /predict` with `{"trip_id":"<id>"}` - predicted route, per-point arcs, route continuity diagnostics, timings, and aggregate evaluation when a reference route is available;
- `GET /docs` - interactive API schema.

The prediction response uses `[lat, lon]` coordinates. It contains predicted paths and aggregate metrics only; it never returns reference geometry or per-point reference labels. Requests and results are logged in the API laptop's terminal.

## Current limits

The API expects the approved runtime trip directory to be available on Laptop 1. Raw dataset files are not stored in this repository. Student-test use in the commands above is for development/demo checks only. Final evaluator data must be supplied through the authorized evaluator process.
